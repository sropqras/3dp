# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Two things for a Klipper 3D-print farm:

1. **`farm/`**, a production pipeline and a web control room, run as `python -m farm`. It uses Python 3.10+ and the **standard library only**, so don't add dependencies.
2. **Config backups and farm docs.** `printers/<Name>/` holds Klipper/Moonraker configs pulled from the printer hosts, `prusa/` holds the PrusaSlicer 2.9.6 profiles, and `FARM.md` has the printer list, feature matrix, staged changes and change log.

Read `HANDOFF.md` for current state, and work from its **"To do (in order)"** list. The first items are Ironman's: applying the changes staged in the Printers tab (an agent never applies them), then `python -m farm audit <printer>` must pass.

aali-cli is now the only place work continues. The Windows workstation no longer pushes, and must `git pull` before any use. Read `PIPELINE.md` for the stages and the human visual gates.

## Commands

```bash
python3 -m farm status [printer]              # live printer state via Moonraker
python3 -m farm audit [printer]               # live Klipper config vs farm baseline rules; exit 1 on any FAIL
python3 -m farm run jobs/qabrastaan/A01.json  # likhan -> slice -> M600 -> checks inline; no printer contact
python3 -m farm submit <job.json>             # same pipeline, queued for the worker (Farm Control shows it)
python3 -m farm worker [--once|--alive]       # the worker (aali-cli: jobctl farm-worker keeps it running)
python3 -m farm run <job.json> --upload       # ...then upload to Moonraker
python3 -m farm start runs/<stamp>_<job>      # only after the human visual gate
python3 -m farm watch runs/<stamp>_<job>      # follow until first layer / colour change / finish / error
python3 -m farm serve --port 10111            # Farm Control web UI (LAN only, no auth)
python3 -m farm monitor [--state FILE]        # one read-only pass of the serious-error monitor (jobctl farm-monitor runs it)
python3 -m farm inventory import|sync         # refresh the Inventory from every printer (read-only) + the OMV NAS list (jobctl farm-inventory: hourly)
python3 -m farm inventory nas-import <path>   # fetch ONE NAS model into data/nas/ as an Inventory artefact
scripts/backup-configs.sh [ssh-host]          # pull configs from enders3dp into printers/
```

Tests: `python3 -m unittest discover -s tests -t .` (stdlib, offline; one module: `python3 -m unittest tests.test_gcode`).
Golden G-code: `python3 tests/golden.py check`. It needs likhan and the slicer but no printer, and proves a refactor didn't change what reaches a printer. Re-record with `record` only after an intended change, such as a new slicer version or preset. `python3 -m farm doctor` checks this host is ready to produce.
The plan being implemented, phase by phase, is in `docs/ARCHITECTURE.md`.

Host settings come from env vars in `farm/config.py`. The defaults suit the user's Windows workstation, so on aali-cli set:
`FARM_PRUSASLICER="flatpak run --command=prusa-slicer com.prusa3d.PrusaSlicer"` and `FARM_LIKHAN_URL=http://127.0.0.1:4111`. `FARM_FONTS_DIR` defaults to `assets/fonts/`. Licensed fonts are gitignored and never committed.

## Architecture

- **`printers/registry.json` is the registry** (loaded by `farm/printers.py`; `FARM_REGISTRY` overrides the path in tests) and the single source of truth the code uses. Each printer has a Moonraker URL, usable bed area, max Z, `has_m600_prompt`, the profiles it may use, legacy preset names, and `readonly`.
  - A **person** adds or changes printers in the Printers tab (onboarding checklist → **Add to the farm**; **Farm settings** for watch-only and profiles). Only `ui:`/`cli:` actors may write it, every write lands in FARM.md's change log, and the web server and worker reload it on change (no restart). An AI session doesn't edit `registry.json` by hand; commit the tab's edits in a development session.
  - Its hardware facts must match `FARM.md`. Don't add a printer without confirmed hardware. A profile is only saved for a printer whose bed fits it.
  - `readonly=True` printers are shown and audited but never sent jobs or config changes. (EnderV3SE was one until Ironman handed it over on 2026-10-23.)
- **The pipeline runs on DB rows** (`farm/db.py` sqlite, `farm/jobs.py` state machine, `farm/pipeline.py` steps). An order has jobs (items), each job is generated by its **maker plugin** (`farm/makers/`, contract `farm-maker/1`; likhan is the first adapter). `plan` puts jobs on builds (a `bed_group` shares one bed), `slice` takes a build to `review`, and a **person** approves (`jobs.TRANSITIONS`: only `ui`/`cli` actors). Only approved builds are uploaded, and approval refuses G-code not sliced by PrusaSlicer 2.9.6. Adapters exist for all five makers (`likhan`, `lithophane`, `lamp` + `plaque`, `namakdani`, `holder` async/experimental). `tests/test_maker_contract.py` is offline; `tests/live_makers.py` runs each against the real apps (no printer). Farm Control's **+ New job** renders each maker's form from its spec. Licensed fonts are picked by name from `assets/fonts/` and are never uploaded or served. `farm/worker.py` runs the steps as leased tasks, one at a time, with retry for transient maker failures. `farm run` calls the same steps inline. Plan and phases: `docs/ARCHITECTURE.md`.
- **`farm/profiles.py`**: a job picks a print **profile** (a reviewed printer + print + filament preset set, plus the printers that can run the same G-code, allowed layer heights and a volumetric cap) + layer height + printer. A job JSON without `"profile"` maps to `neo-petg-036`, today's presets exactly. Farm-owned presets live in `prusa/farm_profiles.ini`; the user's own bundles are never edited. `python3 -m farm presets check` checks every profile statically. A profile with `confirmed=False` slices for review but refuses upload.
- **Pipeline (`__main__.cmd_run`).** A job JSON (`jobs/*/`) produces a `Run` (`runlog.py`, `runs/<stamp>_<slug>/` holding `run.log`, `manifest.json`, the STLs, `presets/`, the G-code and `.3mf`). The stages are:
  1. `likhan.generate` calls the external likhan-maker HTTP service. Bed size is overridden from the registry, not taken from the job.
  2. `slicer.slice_model` extracts presets from the `prusa/*.ini` bundle, aligns the first-layer height so every colour-change Z lands on a layer top, inserts `M600`, and lays out multi-plate beds as a 3MF.
  3. `gcode.validate` runs static checks on the output G-code.
  4. `project.export_project` writes the `.3mf` the human opens for the visual gate.
  5. `moonraker.upload`/`start` handle the printer side. `start` refuses unless Klipper is ready and not printing or paused, and it logs audit failures first.
- **A job with `"plates"`** puts several labels on one bed. Without it, one design is auto-split into pieces, and each piece gets its own bed. `"base_top"` in `colour_changes` resolves to `base_thickness_mm`.
- **`farm/audit.py`** encodes every lesson learned on any printer as a rule run against the **live** config (`/printer/objects/query?configfile=settings`). Each rule states why it exists. When a new printer problem is found, add a rule here so it's checked farm-wide.
- **`farm/web.py`** + `static/index.html` make up the control room. The server alone talks to the printers. The page polls `/api/overview`, cameras are proxied through `/api/cam/<printer>`, and spools live in the farm DB (Spools tab; `data/inventory.json` was only the seed). The 3D viewer is hand-written WebGL2 in the page, with no libraries. It fetches `/api/model/<run>/<file>`, which `farm/model3mf.py` builds from the run's project `.3mf` (bed-space meshes plus the file's own colour changes, layer heights and bed shape). Jobs link to printers by matching uploaded remote paths in `runs/`, so runs made on another host don't link.
- **Look and layout** (`static/farm.css` + `static/ui.js`, shared by both pages, served from an allowlist in `web.py`):
  - Themes are token blocks in `farm.css` (dark, light, and System following the device). Colours appear only in
    token declarations; `tests/test_static_ui.py` fails on a literal colour anywhere else. Data colours (spool hex,
    colour pickers) come in through `${...}`.
  - The ⚙ menu sets theme, density, text size and card size. **Edit layout** (Fluidd-style) moves, hides and collapses
    sections (`<section class="panel" data-panel>` in a `data-panels` container) and cards (`data-card`; the page asks
    `farmUI.cardState()` while building each card, so the poll's re-render keeps the layout).
  - All of it is per browser (`localStorage["farm.ui.v1"]`), not farm state. A card that needs attention (offline,
    error, paused, an alert, PrintGuard ⚠, staged changes, maintenance due) is never hidden, only shown collapsed.
- **`farm/monitor.py`** is the serious-error watch. It alerts on Klipper error/shutdown, a print in the error state, Moonraker down two polls running, and new console `!!`/`Unknown command` lines. It's stateful, so it reports only new problems (loud) and recoveries (silent). On aali-cli the jobctl job `farm-monitor` runs it every 2 min and sends alerts through the ops Telegram bot. Each `Printer` carries its `fluidd` URL. Fluidd can't choose an instance from the URL, so a shared Fluidd gets a `fluidd_note`.
- **PrintGuard** (`farm/printguard.py`; setup in `~/agent_workspace/infrastructure/printguard/`) is failure detection by
  a local vision model on 3dpnas:11111. The farm only reads its REST API (read scope).
  - `farm-monitor` relays each new PrintGuard alert loud, once ("Not paused - check the camera"). PrintGuard unreachable,
    or a printing printer it gets no frames from, is a quiet, debounced note.
  - Printer cards show a PrintGuard badge (standby / score / ⚠ alert).
  - Its monitors are alert-only (`on_defect: none`); `configure.py` there sets them. Never switch one to pause or
    cancel, or point anything at its control API, without Ironman's per-printer decision.
  - `FARM_PRINTGUARD_URL` lives in `farm.conf`. A token (`FARM_PRINTGUARD_TOKEN`) is needed only once one is issued
    in PrintGuard.
- **The Printers tab** (`/printers`; `farm/hosts.py`, `farm/fleet.py`, `farm/configs.py`, `farm/cfgchange.py`, `farm/baseline.py`, `farm/ops.py`) is how printers are maintained without an AI session:
  - fleet health per host (`printers/hosts.json`);
  - config snapshots and drift against a reviewed reference (nightly jobctl `farm-backup`);
  - staged config changes with a gated Apply, verify and rollback;
  - **Stage fix** for every audit rule with a generated fix (`baseline.fixable`);
  - the Telegram pack (never stores the token);
  - service restarts gated by what they disturb;
  - USB devices over read-only SSH;
  - root-only host steps as scripts for a person to run with sudo.

  Plan: `docs/PRINTERS_TAB.md`.
- **Inventory, Projects, NAS** (`docs/FARM_PROJECTS.md`):
  - **`farm/inventory.py`**:
    - Artefacts are maker jobs, printer G-code, NAS imports and items.
    - Prints come from Moonraker history (read-only, every registry printer) and the tracker.
    - Everything is folded into designs by `design_key()`, which maps PrusaSlicer's `<name>_<time>_<layer>mm_...gcode` back to `<name>`.
    - Good/Bad marks and portfolio products are a person's.
  - **`farm/nas.py`**:
    - Catalogues `\\OMV\3dprinting\3dprinting\Project Files` (and `ProductImages`) with `rsync --list-only` over the OMV rsync daemon.
    - Never copies in bulk; Import fetches one file.
    - A failed or partial listing (rsync 23/24) never marks files gone. An unchanged listing (same hash) writes
      nothing. `nas.status()` says online/offline, and offline the catalogue and previews come from the cache.
    - **Catalogue 2.0** (Inventory → NAS catalogue): folder tree / farm categories, facet chips, Grid / Table /
      Matrix, saved views, pack drawer.
      - `farm/nasindex.py`: categories as rules (folder subtree < file override; filename `match`), seeded once,
        and tags from names.
      - `farm/nasview.py`: query, facets, tree, packs and edits (person only).
      - `farm/meshprev.py`: stdlib STL/3MF previews and a PNG rasteriser.
      - Previews live in `data/nas/_thumbs` and `_preview`, valid while size and mtime match; full meshes go in
        the bounded `_cache` (10 GB).
      - jobctl `farm-nas-thumbs` (01:30, 50 min) warms them. The web server's builder thread does what people
        are looking at, two builds at once at most.
  - **`farm/projects.py`**:
    - A large order is groups → parts × qty.
    - A part is made from a New-job template (its label personalises it), re-prints an artefact, or is a bought item.
    - Generate and Send only prepare.
  - **`farm/makers/upload.py`**: takes a person's STL/3MF through the normal gates.
- **The farm standard** (`farm/standard.py`, `printers/standard/farm_macros.cfg`, `docs/FARM_STANDARD.md`):
  - One macro library, the same file on every printer, with each printer's numbers in `[gcode_macro _FARM_PRINTER]`.
  - Installed and upgraded by the audit rule "farm macro library is current" (a WARN with a generated fix: two staged
    changes, library first; the gate refuses an include whose file another staged change creates).
  - Change a shared macro in the repo file and bump its `variable_version`, never on one printer.
  - Fluidd layout (macro groups from the `Group |` description prefix, farm temperature presets) is a person's action
    in the Printers tab, kept in `ui_pushes` for Undo.
- **Restore points** (`farm/restore.py`, Printers tab → Restore points; `farm config origin|points|restore|archive`):
  - Each printer's **original** config (before the farm's first change) is pinned once as a `config_snapshots` row of
    kind `origin` and never re-taken. Files edited before the first farm snapshot come from the host's own
    `<file>.bak-YYYYMMDD-HHMM` copies. It is also kept in git under `printers/_archive/<printer>/origin/` + `ORIGIN.md`.
  - `printers/_archive/<printer>/host|kiauh/` holds the hosts' own history (`.bak`, SAVE_CONFIG `printer-*.cfg`,
    Fluidd zips, KIAUH 2024-25 backups). Secrets are left out by name (`configs.secret`, which covers copies like
    `telegram.conf.bak-*`) and by content. Tarballs are never archived.
  - Snapshots keep file times (`mtimes`), so each config has a live window. Prints that started and finished
    inside it are its evidence ("exact" / "likely"); **last known good** = the newest config with completed prints
    and none marked bad. Calibration prints (towers, cubes, PA tests) never count.
  - A restore stages one change per differing file as a **batch** (`config_changes.batch`, kind `restore`). The gate
    applies a batch together: one snapshot, one restart, all put back if Klipper doesn't load. Audit FAILs the old
    config had are reported, not counted as failure. Rollback and Cancel act on the whole set. The gate also takes
    an "after change" snapshot so the new config is dated from the moment it's on.
  - The nightly `farm backup` pins an origin for any printer without one and archives new history files.
    Committing `printers/_archive` is a development session's job (git is the copy off aali-cli).
- **Printer power** (`farm/power.py`): a Meross MSS426 surge strip (192.168.1.63) switched over its **local** HTTP API
  (signed with the account's device key, `FARM_MEROSS_KEY` in `farm_control/meross.env`, chmod 600, fetched once by
  Ironman with `~/agent_workspace/infrastructure/meross/get_key.sh`). No farm code talks to Meross's cloud
  (`test_no_ai` checks).
  - A printer is switchable only once a person maps it to one outlet in the Printers tab → Farm settings (registry
    `power`: ip, uuid, channel; logged in FARM.md). Channel 0 (the whole strip) is never mapped, and the device is
    identified by uuid **before** anything is sent.
  - The ⏻ control on each printer card, the switched-off card's **Power on** (switch on, then FIRMWARE_RESTART), and
    `python3 -m farm power scan|on|off`. A strip that can't be read is a quiet monitor note.
  - **Named outlets** that aren't printers live in `printers/power.json` (`power.map_aux`, a FARM.md row each). The
    first is **"Farm lights"**: channel 7, the strip's USB ports, for USB LED lights when the garage is dark (2026-10-24).
    A person switches them with the 💡 button in the dashboard header. There are no print checks (nothing to protect),
    but the strip is still identified first and channel 0 is never used. A printer can't be mapped to a named outlet.
- **Switched-off printers** (`monitor.powered_off`): the farm switches idle printers off.
  - "Unable to connect" or "Lost communication" while nothing prints is a silent note, not an alarm.
  - **Reconnect** (FIRMWARE_RESTART) is offered only from that state, never on a watch-only printer.
  - Losing the board mid-print stays loud.
- **Health alerts are debounced** (`monitor.settle`): a problem is told once it has lasted (2 passes loud, ~25 min
  silent) and "recovered" once it has stayed gone as long, so a crash-looping Telegram bot is one message, not one per
  pass.
- **Who did it:** every page action carries an `operator`, recorded as `ui:<name>`. The name is the header's
  "You: <name> ✎" link (`static/operator.js`, served with `config.OPERATOR` = env `FARM_OPERATOR`, default
  "Ironman"). Clicking it changes the name for that browser only. It's attribution, not authentication.
- **The web API refuses cross-site POSTs**: every POST needs the `X-Farm: 1` header the pages send (and a same-host
  Origin), and only the page's own viewer counts as "viewed" for the gate. Scripts that POST must send it too.
- **`farm/net.py`** holds the stdlib HTTP helpers. Use it rather than adding `requests`.

## Rules

- **The farm runs without language models or paid/cloud AI.** No farm code, page or job calls a language model
  (Claude, OpenAI, Ollama, ...) or a cloud or pay-per-use AI service. The pipeline, the worker, Farm Control, the
  monitor and the makers are deterministic tools (`tests/test_no_ai.py` enforces it). The jobctl `farm-*` jobs set
  `AI_ESCALATE=0` (no Claude diagnosis on repeated failure) and `NOTIFY_PLAIN=1` (no Ollama summaries). Claude
  sessions are for developing the tooling only; never add a step that needs one.
  - **Allowed (Ironman, 2026-10-23):** a **local vision model** that costs nothing per use and sends nothing off the
    LAN. The first is PrintGuard for print-failure detection, running in its own container. Farm code may read its
    results only from a LAN/Tailscale address (`FARM_PRINTGUARD_URL`, checked by the test). A detector may alert;
    pausing a print automatically is a per-printer decision Ironman makes after an alert-only trial (started
    2026-10-23, alerts through farm-monitor).
- **Printer configs change only through Farm Control's Printers tab** (`/printers`, `farm/cfgchange.py`). An AI session may *stage* a change with a reason (`python3 -m farm config stage --printer <name> --path printer.cfg --section printer --option max_velocity --value 200 --reason "..." --author agent`), but never applies or rolls one back on its own, and never edits printer files over SSH or the Moonraker file API directly. A person presses Apply. The one exception: Ironman names the specific change ids in the session and says apply them (as on 2026-10-23 for changes 4 and 7). The session then runs them through the same gate as `cli:Ironman`, and that permission covers only those ids. The gate refuses while printing or paused, takes a snapshot, verifies (Klipper ready, no new audit FAIL, no `Unknown command`), rolls back automatically if Klipper doesn't come back, and writes FARM.md's change log.
- **Printer power is a person's action.** Agents never switch an outlet (no POST to `/api/fleet/*/power`, no
  `farm power on|off`), and neither does the monitor. `farm/power.py` refuses Off while printing or paused, with any heater
  target set, with the hotend at 50 °C or more (its fan needs power to cool it), or when Moonraker can't be read,
  unless the board is already gone. Watch-only printers get no power control. `farm power scan` is read-only and fine.
- **Agents never approve or start prints.** No calls to `/api/builds/*/approve|start`, `farm approve` or `farm start` (the latter two refuse without a terminal anyway). Preparing, slicing and queueing for review is fine. Only `farm/gate.py` can start a print: `moonraker.start` needs its token, and the gate re-checks the approval hash, the 3D view, the audit, printer idle, the uploaded file and the spool.
- **Visual gate, the most important rule:** never run `farm start` (or start a print any other way) until the user has looked at the run's `.3mf` (Farm Control's 3D viewer or PrusaSlicer), confirmed the bed is clear and the first colour is loaded, and said go. Preparing and uploading a run is fine. Starting one on your own is not.
- **EnderV3SE (enders3dp:7128) was handed over to the farm on 2026-10-23.** It is Ironman's own production printer: it gets changes through the gate like the others, but only while it is idle and never between his prints without asking. It has no print profile yet, so no farm jobs go to it until one is confirmed.
- **The Charles Wright Bold font is a paid licence.** Never commit it, never serve it publicly (not through Farm Control, not in an artifact), and never fetch it automatically. It is copied by hand into `assets/fonts/`. Installed on aali-cli 2026-10-23 (from Ironman's own upload, at his request), at mode 600. With it, R50 at the batch standard measures 154.8 mm of text and 71.1 mm letter height.
- **After any macro change, read the console:** `GET /server/gcode_store` and look for `Unknown command`. Moonraker's `ok` from `/printer/gcode/script` doesn't prove the macro ran. That is how a misnamed macro hid the colour-change prompt on 2026-10-22.
- **Never restart Klipper or edit configs on a printer that is printing or paused.** Check `farm status` first. Changes waiting for a print to finish go into FARM.md's "Staged, not yet on the printer" table.
- After any printer config change, `python -m farm audit <printer>` must pass. Record the change in FARM.md's change log and feature matrix.
- In the feature matrix, `?` means unconfirmed. Configs contain copy-pasted sections, so don't infer hardware from them.
- `printers/` backups exclude secrets (`telegram.conf`, `moonraker-obico.cfg`, `octoeverywhere.conf`), and `.gitignore` excludes them too. Keep it that way. Symlinked upstream code (KAMP, fluidd.cfg, timelapse) is recorded in `SYMLINKS.txt`, not copied.
- enders1plus (3dpnas) is changed like every printer, through the Printers tab (Moonraker's file API). aali-cli's read-only key (`~/.ssh/enders3dp`) is authorised on 3dpnas since 2026-10-23, so its USB device listing works. 3dpnas will also host PrintGuard (port 11111, `~/agent_workspace/infrastructure/printguard/`).
- **Never edit a DB migration that may have run.** The every-2-min `farm-monitor` job runs straight from the working tree, so a migration is applied to the live DB the moment it's saved. Add a new numbered migration instead, with `IF NOT EXISTS` if a draft got out.
- Macro names like letter+digits (e.g. `_A1`) get parsed by Klipper as classic G-code commands, and the audit flags them.
- aali-cli has the apt `prusa-slicer` **2.7.2** at `/usr/bin/prusa-slicer`. It's fine for testing, but production G-code needs 2.9.6 (Flathub).
- Known PrusaSlicer 2.9.6 CLI quirk: it segfaults on `*_extruder = 0` keys. `slicer.extract_preset` strips them.
- If Farm Control or any job is deployed to run on aali-cli, record it in `/home/aali/agent_workspace/SERVER.md`.
